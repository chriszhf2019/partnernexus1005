## 一、页面整体信息架构（四层递进结构）

页面从顶部导航开始，自上而下呈**宏观 → 诊断 → 行动计划 → 具体业务操作**的四层递进结构。

```
┌────────────────────────────────────────────────────────────────┐
│  系统主导航（合作伙伴 / 商机 / 市场营销【激活】 / 激励政策 ...）│
├────────────────────────────────────────────────────────────────┤
│  顶部操作栏（页面标题 + 【年度预算规划】跳转 + 【+ 新活动】）   │
├────────────────────────────────────────────────────────────────┤
│  黑底 Banner：生态健康度仪表盘                                 │
│  ├── 三维度得分：覆盖率 / 活跃度 / 效率                        │
│  └── 综合健康度分数 + 快速统计（活动数 / 待推进 / 线索总数）   │
├────────────────────────────────────────────────────────────────┤
│  第一层：4 卡片 KPI                                            │
│  ├── 活动推进（完成率 + 时间进度对比）                          │
│  ├── 预算执行（支出/预算 + MDF vs 自办执行率）                  │
│  ├── 线索产出（累计线索 + 场均线索 + MQL/SQL 估算）            │
│  └── 商机转化（商机数 + 金额 + ROI + 新客户占比）               │
├────────────────────────────────────────────────────────────────┤
│  第二层：3 卡片诊断                                            │
│  ├── 进度/核销：待完成活动清单 + 核销滞后告警                   │
│  ├── 质量/转化：跟进率 + 线索→商机转化率 + 转化周期            │
│  └── 最佳实践：Top 活动类型 + SOP 下载数 + 建议推广            │
├────────────────────────────────────────────────────────────────┤
│  第三层：行动计划（0-4 项动态生成）                            │
│  ├── 待推进活动 / 核销滞后 / MDF 激励跟进 / 渠道激活等          │
│  └── 每项含优先级 + 建议文案 + 可扩展明细                       │
├────────────────────────────────────────────────────────────────┤
│  第四层：活动详细列表（左侧 2/3 + 右侧 1/3）                  │
│  ├── 左侧：活动列表（状态过滤 + ROI 排序 + 进度条）            │
│  └── 右侧：伙伴矩阵 / 最佳活动 ROI / 活动类型分布饼图          │
└────────────────────────────────────────────────────────────────┘
```

## 三、核心数据模型

### 3.1 主数据源：mdfActivities（营销活动明细）

来自 `useMarketingData().mdfActivities`，字段覆盖 24+ 个核心属性：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `string` | 主键 |
| `name` | `string` | 活动名称 |
| `type` | `string` | 活动类型（线下峰会 / 沙龙 / Webinar 等） |
| `status` | `'Planning' \| 'In Progress' \| 'Completed'` | 执行状态 |
| `hostType` | `'partner' \| 'vendor'` | 主办方类型（伙伴合办 / 厂商自办） |
| `budget` | `number` | 计划预算 |
| `actualSpend` | `number` | 实际支出 |
| `leads_generated` | `number` | 产生线索数 |
| `mql_count` | `number` | MQL（市场认可线索）数 |
| `sql_count` | `number` | SQL（销售认可线索）数 |
| `deals_created` | `number` | 产生商机数 |
| `deals_amount` | `number` | 商机金额 |
| `expected_attendees` | `number` | 预期参与人数 |
| `new_logo_count` | `number` | 新客户数 |
| `new_logo_amount` | `number` | 新客户订单金额 |
| `grade_a_leads` / `grade_b_leads` / `grade_c_leads` | `number` | A/B/C 级线索分布 |
| `conversion_days` | `number` | 平均转化周期（天） |
| `follow_up_rate` | `number` | 跟进率（%） |
| `stale_leads` | `number` | 超过 48h 未跟进的线索数 |
| `sop_downloads` | `number` | SOP 材料下载次数 |
| `province` / `city` | `string` | 活动举办省份/城市 |
| `partner_id` / `partner_name` | `string` | 关联伙伴 ID + 名称 |

### 3.2 预算配置：marketing_budget_config

来自 `supabase.from('marketing_budget_config')`，存储年度预算总量和各季度分配。

### 3.3 计划数据：marketing_plan

来自 `supabase.from('marketing_plan')`，存储每个季度的活动计划（区别于实际执行记录 `mdfActivities`）。当前季度（Q2）执行中的活动会从该表加载到 `q2Plans` state 中。

### 3.4 伙伴数据：partners

来自 `supabase.from('partners')`，用于伙伴下拉选择和伙伴矩阵 tier 分布计算。

## 四、核心业务逻辑

### 4.1 数据获取链路

```
useMarketingData() [hooks/useData.ts]
       │
       ├─ mdfStats          → MDF 活动统计（预算/申请/核销）
       ├─ mdfActivities     → MDF 活动明细（核心数据源）
       ├─ incentivePrograms → 激励政策配置
       └─ incentiveStats   → 激励政策统计

useEffect() [MarketingIncentivePage.tsx 第 139-151 行]
       │
       ├─ marketing_budget_config  → 预算配置（年度/季度预算）
       ├─ marketing_plan (Q2)       → 当前季度活动计划
       └─ partners                  → 伙伴字典
```

### 4.2 关键派生指标体系

所有动态指标通过 `useMemo` 计算，避免重复渲染。

```typescript
// ① executionProgressData（第 178-304 行）
{
  execRate:        totalSpend / totalBudget * 100       // 预算执行率
  timeProgress:    (monthIndex % 3 + 1) / 3 * 100       // 时间进度（季度内）
  completionRate:  completedCount / totalActivities * 100 // 活动完成率
  isLagging:       completionRate < timeProgress - 10   // 进度滞后（差距>10%）
  hasReconciliationLag:  // 已完成但 actualSpend === 0
  regionDistribution:    // 省份→大区映射（华东/华南/华北等）
  mdfBudget / selfBudget:  // MDF（伙伴领用）vs 自办预算
  mdfExecRate / selfExecRate:  // 两类活动的执行率
  activityTypesDetailed:  // 按类型统计（含异常检测）
}

// ② executionQualityData（第 306-358 行）
{
  cumulativeParticipants:  // 累计参与人数
  avgLeadsPerActivity:   // 场均获客数
  last30Days:             // 近30天参与人数走势（用于迷你趋势图）
  topActivities:          // Top5 活动（综合权重：参与×1 + 线索×3 + 商机×5）
  activityHeatmap:        // 活动类型热度排行（按场均线索排序）
}

// ③ conversionData（第 360-408 行）
{
  totalDeals / totalDealsAmount:    // 商机总数 + 金额
  avgConversionRate: totalDeals / totalLeads * 100  // 线索→商机转化率
  newLogoCount / newLogoPercentage:  // 新客户数 + 新客户占比
  gradeA / gradeB / gradeC:         // A/B/C 级线索分布（无数据时估算）
  avgConversionDays:                 // 平均转化周期
  followUpRate:                      // 跟进率
}

// ④ diagnosticData（第 412-682 行）
// 诊断A：执行与预算错配
{
  isGlobalMismatch:  completionRate 与 execRate 偏差>20%
  regions:           预算占比>10%但完成率<60%的问题区域
  mdfProblem:         MDF执行率<40%的问题检测
  reconciliationIssue: 已完成但支出为0的核销滞后
  summary:            综合诊断结论文本
}

// 诊断B：线索"肠梗阻"分析
{
  lowConversionActivities: 参与者≥10但转化率<30%的活动
  lowFollowUpActivities:   跟进率<60%的活动
  longConversionActivities: 转化周期>60天的活动
  summary:                  综合结论
}

// 诊断C：高产出活动复刻分析
{
  typePerformance:    按活动类型聚合（线索/商机/新客/ROI）
  bestByLeads / bestByConversion / bestByNewLogo / bestByROI: 各维度最优
  topRegions:        区域产出排行
  sopDownloadCount:  SOP下载量
  summary:           综合推荐结论
}

// ⑤ actionCards（第 718-855 行）
// 基于上述诊断结果，动态生成 0-4 项行动卡片
// 候选：待推进活动 / 核销滞后 / 线索跟进干预 / 标杆经验推广 / 区域补充
```

### 4.3 关键计算公式

```typescript
// 综合健康度评分
overallScore = Math.round((completionRate + followUpRate + execRate) / 3)

// 预算执行率（注意：可能因 totalBudget === 0 而出现 0%）
execRate = totalBudget > 0 ? (totalSpend / totalBudget) * 100 : 0

// 线索→商机转化率
avgConversionRate = totalLeads > 0 ? (totalDeals / totalLeads) * 100 : 0

// ROI（当前口径：每万元预算产出线索数）
roi = budget > 0 ? (leadsGenerated / (budget / 10000)) : 0

// 时间进度（季度内）
quarterNum = parseInt(currentQuarter.replace('Q', ''))  // 1-4
quarterStartMonth = (quarterNum - 1) * 3               // 0, 3, 6, 9
monthsIntoQuarter = monthIndex - quarterStartMonth + 1  // 1-3
timeProgress = (monthsIntoQuarter / 3) * 100           // 0-100

// 进度是否滞后（完成率显著低于时间进度）
isLagging = completionRate < timeProgress - 10

// 区域映射逻辑
province → 大区
  上海/江苏/浙江/安徽/福建/江西/山东 → 华东
  广东/广西/海南 → 华南
  北京/天津/河北/山西/内蒙古 → 华北
  河南/湖北/湖南 → 华中
  重庆/四川/贵州/云南/西藏 → 西南
  陕西/甘肃/青海/宁夏/新疆 → 西北
  辽宁/吉林/黑龙江 → 东北
```

## 八、当前设计与实现中的关键痛点

### 8.1 宏观与微观数据脱节
* `mdfStats`（聚合统计）vs `mdfActivities[*].progress`（活动级进度）来源不一致
* 顶部大数字与列表中单个活动的完成率缺乏同步校验

### 8.2 ROI 指标口径模糊

```typescript
// 当前：每万元预算产出线索数（不是真正的 ROI）
const roi = budget > 0 ? (leadsGenerated / (budget / 10000)) : 0;

// 建议改为：商机价值 / 实际支出（业务语义更准确）
const trueROI = actualSpend > 0 ? (dealsAmount / actualSpend) : 0;
```

### 8.3 时间进度计算失真

当前公式：`timeProgress = ((monthIndex % 3) + 1) / 3 * 100`

结果：季度内时间以**月为单位跳变**（第1月=33% → 第2月=66% → 第3月=100%），不连续，导致季度中段查看时显示进度跳跃。

建议改为：**每天均匀递增**，或基于 `Date.now()` 与季度首日的精确差值计算。

### 8.4 活动类型无归类

当前 `type` 字段为原始字符串（可能 10+ 种），饼图可读性差。建议归并为 5-6 大类：线下活动 / 线上活动 / 联合营销 / 渠道招募 / 赋能培训 / 其他。

### 8.5 诊断维度缺失

当前仅覆盖：进度 / 质量 / 最佳实践。建议补充：

* **区域维度** — 华东/华南/华北的执行差异（已有数据，未可视化）
* **伙伴类型维度** — 金牌 vs 基础伙伴的产出对比
* **投入产出比维度** — 高预算活动是否带来了高商机转化

### 8.6 行动卡片无 CTA

卡片仅展示文本，缺少「一键催办」「生成报告」「分享给伙伴」等可操作按钮。没有状态反馈（已点击/已完成）。

### 8.7 空状态不友好

当 `totalBudget === 0`（预算未配置）时，页面显示执行率 `0%`，但实际含义是「待预算审批」，应引导用户前往 `/marketing/plan`。

### 8.8 状态管理冗余

`selectedActivity`、`selectedActivityFunnel` 等多个 `useState` 在当前版本中没有消费方（历史遗留代码），会增加维护负担。

### 8.9 国际化不完全

部分文本硬编码中文（如「待推进」「超支」「紧急」「基础伙伴」），未统一使用 `t()` 函数。

## 九、推荐的下一步优化方向

| 优先级 | 优化项 | 预期价值 |
|--------|--------|----------|
| **P0** | ROI 公式重定义（商机价值/实际支出） | 决策指标更准确 |
| **P0** | 行动卡片 CTA 化（催办/报告/分享按钮） | 打通「诊断→行动」闭环 |
| **P0** | 预算为空时的友好提示（引导配置预算） | 降低用户困惑 |
| **P1** | 时间进度精确计算（每日均匀递增） | 避免进度跳变 |
| **P1** | 区域热力图（已有数据，可视化展示） | 补充缺失诊断维度 |
| **P2** | 活动类型归类（合并为 5-6 大类） | 提升饼图可读性 |
| **P2** | 诊断覆盖扩展（伙伴类型/规模维度） | 更全面的业务洞察 |
| **P3** | 清理冗余状态（selectedActivity 等遗留代码） | 降低维护成本 |
